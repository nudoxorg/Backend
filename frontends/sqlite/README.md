# Experimental SQLite native adapter

Pinned upstream syntaqlite `4e4de76312429fb2235ae093ab2125914320d5bd`, version 0.13.5, Apache-2.0. It uses SQLite-derived C grammar/tokenizer with Rust bindings; this is not a PostgreSQL parser. Its path checkout is an external research dependency, so this package remains nonportable and is excluded from the product workspace. The compile uses SQLite, fmt and analysis features: SQLite alone failed in this revision because upstream imports fmt-gated modules.

The shared SQL contract includes dialect, engine revision, source digest and honest parse/binding coverage. The SQLite adapter supplies native parse results and MissingContext, with lexical identifiers explicitly unavailable. A one-shot worker uses the shared process framing. A separate test exercises the actual native analyzer with a declared synthetic catalog and validates an unknown column diagnostic; this is not wired to product binding. The checked path records syntaqlite version/cflags and analyzer DQS behavior and uses the existing supervisor and source verifier; canonical catalog identity and installation admission remain open. No database, SQL execution or migration is involved.

The worker also accepts an adapter-specific `ProposedCatalog` (sorted tables and column names, explicit epoch, bounded canonical JSON); the result carries its digest and native diagnostic kinds/byte extents. This is caller-proposed context, not admitted catalog identity or complete binding evidence. The fixture always supplies a known column list; syntaqlite conservatively accepts unknown columns when a list is absent, so absence of diagnostics is never presented as an exact reference or complete graph. SQLite's default double-quoted-string fallback is demonstrated separately from PostgreSQL. This profile has no custom functions, extensions, attached databases, or dynamic dialects; the recorded analyzer settings are not a durable workspace configuration root or a claim about any real SQLite connection.
