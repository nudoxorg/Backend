# Embedding pipeline baseline

## Dataflow

Compiler-source embedding begins after a package's selected files have entered the compiler. C, C++, C#, Go, Java, Python, Rust, and TypeScript package profiles converge on `LocalCompilerExecution::stage_package_sources`; language-specific authority and lowering produce one semantic image per successfully compiled source. The embedding inputs are those exact admitted UTF-8 source strings. Rust files outside the active Cargo target are recorded as coverage gaps and do not become embedding inputs. Compiler embeddings are optional by default and are emitted as a versioned `BVE1` float32 payload tied to the activated model recipe.

The local query path remains independent. It builds its local answer and lexical lane from the coordinator's admitted local view before optional semantic acceleration. A missing, unhealthy, or failed embedding provider returns that local answer. The remote Qdrant path separately obtains semantic documents from `QueryCoordinator::semantic_documents()`, embeds each document with document treatment, projects vectors under the active Qdrant recipe, and embeds a query with query treatment only after a compatible projection is active.

Before this change, package compilation invoked the external embedding program once for each compiled source. The Qdrant JSON-v1 producer also launched once per distinct document input. Both paths preserved exact model and tokenizer byte revisions, but Qdrant's JSON-v1 wire format was separate from the compiler's supervised BEM1/BEC1 protocol. No in-repository model implementation or GPU inference backend was present.

## Bounded batch path

The compiler now gathers all successfully compiled source inputs and submits them together to `EmbeddingExecutable::infer_batch_with_cancellation_flag`. Exact duplicate `(configuration, purpose, UTF-8 payload)` identities are folded before dispatch. A BEM2/BEC2 worker receives bounded microbatches (at most 256 unique items and within the process input/output byte caps); the runtime admits the response only when every item ID, count, dimension, byte extent, coordinate, and normalization is valid. Activation proves the batch protocol with two distinct query inputs before it selects BEM2. The original BEM1 worker remains supported as a one-process-per-unique-input fallback, and single-item `infer` calls use BEM2 when the active worker passed that batch probe. Successful coordinates are held in a bounded, runtime-local exact-input cache; `probe_ready` bypasses that cache.

Qdrant keeps JSON-v1 as the compatibility default. Setting `BACKEND_EMBEDDING_PROTOCOL=bem2` selects the same production-owned supervised BEM2 runtime used by compiler sources. In that mode, Qdrant submits all unique document cache misses as one bounded batch call, shares immutable `Arc<[f32]>` coordinates with the projection layer, and commits no pending document vectors unless the complete batch validates. Local lexical search never depends on this setting or on Qdrant availability.

The BEM2 request is a fixed 108-byte header followed by items. The header is `BEM2`, task byte (`1` query, `2` document), normalization byte (`0` none, `1` L2), big-endian `u16` dimension, then 32-byte recipe, model, and tokenizer identities, followed by a big-endian `u32` item count. Each item contains a 32-byte `EmbeddingInputIdentity`, big-endian `u32` UTF-8 byte length, and the exact UTF-8 payload. The BEC2 response is `BEC2`, big-endian `u16` dimension, big-endian `u32` count, then one item per request in order: the same 32-byte identity followed by `dimension` little-endian finite `f32` coordinates. No partial count, reordered identity, trailing bytes, or invalid normalization is admitted. Query and document tasks are distinct identities even when their text is equal. The worker reads the verified artifacts through `BACKEND_EMBEDDING_MODEL_FILE` and `BACKEND_EMBEDDING_TOKENIZER_FILE`.

The environment-configured local-service BEM2 producer does not use the compiler's persisted `EmbeddingRuntimeLimits`; it has a fixed worker policy: five-second wall and CPU deadlines, a 20 MiB request/output cap, 64 KiB stderr cap, 256 MiB workspace-growth cap in a private temporary directory, and a 256 per-user process-count ceiling on Unix. 64-bit Linux also applies an 8 GiB per-process virtual-address-space limit. Other platforms retain the portable I/O, wall, and workspace bounds where OS resource limits are unavailable; the explicitly configured local executable remains trusted within that platform boundary.

The activated execution identity also hashes the executable and working-directory paths, exact argument order, and explicit environment values. The private model/tokenizer paths injected into the worker environment are excluded because their byte identities are already included. Per-input cache keys and compiler embedding-plane identities include this launch digest, preventing reuse after an output-affecting launch change. Runtime admission caps newly decoded batch coordinates at 64 MiB, aggregate original UTF-8 input at 512 MiB before identity hashing, input metadata at 65,536 original inputs, and the coordinate cache at 8 MiB. The scheduler's runtime reservation includes input/output buffers, the 64 MiB coordinate cap, a 32 MiB metadata allowance, and the cache; compiler staging separately reserves up to 64 MiB of encoded BVE1 payloads plus its retained input/artifact references.

## Benchmark method and baseline

The deterministic fixture worker uses the same activation, framing, child supervision, identity checks, exact response parsing, cache, and cancellation hooks as production. It has no model-quality role and makes no accelerator claim. In the passing focused test on the M3 Pro host, three document inputs containing two exact distinct payloads used one supervised BEM2 call (versus two cold BEM1 calls); the second identical request used no worker. The measured cold fixture call was 190,212 µs and the exact cache hit was 113 µs. These timings include process startup and fixture work, so they measure duplicate folding and process avoidance, not neural inference throughput. A separate exact-input fixture measured 183 ms cold and 99 µs warm. The Qdrant integration fixture encodes the expected count: one activation probe, then one document-batch process for two distinct semantic payloads plus a duplicate, with no process on the warm projection; its focused test has not yet been run.

Partial counts and mismatched item identities reject a complete microbatch. New embedding-cache entries are committed only after every microbatch in one API call succeeds, so a later failure does not make the earlier part of that call look complete on retry. Cancellation is propagated to the supervised child and waits for termination/reaping. Remote projection admission is transactional: a failed producer call does not replace existing cached document vectors or activate a new Qdrant generation.

The development host reports Apple M3 Pro/Metal 3, but the repository has no native Metal/Core ML or other in-process accelerator provider wired into this path. BEM2 is a provider ABI ready to carry bounded batches to an external GPU-capable worker, but no GPU provider is present or measured in-tree, and no GPU speedup is claimed. Coordinate payloads remain exact float32: quantization or bit-packing would change vector values and the current Qdrant recipe declares float32, so compression is not applied. The only zero-copy optimization here is sharing already validated immutable coordinate storage.
