## Python: recover the lost inference scope without reviving silent fallback

The old Python producer was more than a syntax walker. Pre-cutover `workspace/compiler/languages/src/python/context.rs:239–301` discovers every module, constructs module-name/file handles, runs them together in one `State` transaction and commits it before reading solved exports and class fields. `apply_class` and `apply_fn` at lines 462–490 fill class fields, function returns and parameters. The actual control `an_unannotated_return_gains_the_inferred_class` at lines 776–793 requires the inferred local `Point` return that syntax alone cannot supply. That is a concrete historical semantic capability, rather than an assertion inferred from a test title.

The useful old identity vocabulary is `oracle.rs`: dotted module/class/method identities and overload `#N` branches, exact source extents, explicit superclass types and owned extracted data. `syntax/mod.rs:334–504` records package-local calls against scoped declared/imported names; unresolved and dynamic calls are omitted rather than manufactured. The August 28 `a0228fbb6b` changes the resolver, nominal qualification and recursive type treatment together. Its module discovery and `types.rs` qualified nominal handling are useful parity inputs. They must be translated into the current admitted source/module identity and closed canonical IR; the old owned oracle is not a replacement serving authority.

The cutover itself is unambiguous: `628a6698ca` removes the 1,013-line context and replaces Python lowering with a 60-line primitive assignment scanner (`compiler/driver/lower/python.rs`). Subsequent September work repairs declaration extraction and many canonical shapes. `6e46f27c76`'s `compiler/languages/python/checker.rs:177–182` introduces an inference site contract limited to `ModuleBinding` and `Parameter`. The integrated 039 retains that scope in `frontends/python/src/legacy/checker.rs:203–208`; `build_probe_plan:1350–1355` invokes only parameter and module reveals. `crates/engine/src/driver/lower/python.rs:926–929` creates the function result slot only if `return_annotation` is present. Its class field emitter can consume a keyed inference, but the checker does not probe class fields. A successful type-checker report therefore cannot supply the old inferred return/class-field facts through this interface.

The current boundary also improves an old weakness: `context.rs:169–178` quietly returned syntax-only success when solved types were empty. Current package authority requires the configured Python checker and retains typed selected-tool/transaction failures (`package_authority.rs:387–430`). That truth boundary must stay. Recovery should extend a bounded, source-keyed report with explicit return/field scope, preserve written annotations, distinguish Unknown from proven absence, and project only facts the checker actually established.

For module identity, current package authority calls `analyze_in_package` at line 420. That API validates the package root, but `checker.rs:505–539` writes pristine `module.py` and augmented `probe_module.py` into a private workspace. `run_check:591–594` sets the package root only as cwd. It does not retain the original selected module's relative location or package ancestry. The checker thus analyzes a different module path from the selected source. Tests must cover `pkg/__init__.py`, `pkg/core.py`, `pkg/use.py` using `from .core import Point`, same-spelled classes in another package module, and references/inferred factories that must resolve to the exact source declaration. A helper report or syntax-only extraction is insufficient product acceptance.

It adds `application/python_host.rs`, request-scoped frontier/witness admission, one-shot source consumption, bounded profile/chunk batches, cancellation/deadline handling and strict diagnostic path partitioning. It is valuable for execution amortization and exact batch identity. It does not itself restore the old original-module naming or return/field inference. These two foundations must not be conflated.

## Go and TypeScript: preserve source authority while restoring relationships

Pre-cutover Go lowering (`workspace/compiler/languages/src/go/lower/mod.rs:408–442`) wraps each actual Go package as a module, names it by its import path, attaches package documentation and lowers declarations under that namespace. August 28 `618622fe5768ad279af989b122e1412c007a5054` expands receiver-qualified method references and cross-package nominal handling, using `go/types` rather than spelling scans.

The current producer has substantial stronger surviving foundations. `frontends/go/src/legacy/oracle/main.go:224–230` selects the package owning the bound source; the module root supplies import resolution, while unrelated subpackages are dependencies. `image.go:956–966` rejects duplicate/out-of-order package paths, and lines 1008–1009 bind declaration source extents only to the actual selected file. The Uses/Selections extraction records richer calls, fields and package references. Current lowering keeps cross-file sources distinct rather than borrowing the caller's source coordinates. These are intentional precision improvements, not regressions to undo by restoring a whole-module walk.

The unresolved projection gap is separate. `crates/engine/src/driver/lower/go.rs:2400–2403` skips package documentation, and its test `package_docs_stay_image_only_without_owner_facts:7527–7540` positively requires the projected doc plane to be empty. The old package-level documentation was meaningful data, so preserving it only in an inaccessible image plane is not equivalent public capability. The same lowerer lacks an emitted import-path module owner. Its source claims “complete semantic fidelity” while documenting and testing image-only data; an image producer's success must not be used to claim public docs/namespace projection.

An existing repair foundation is `2e03d3ab9e059640bdee3e6b83772adfd03cb1f1`, dated September 5, not an ancestor of 039. Its exact patch adds package facts before declarations, exact image-validated import-path lookup, declaration-to-package parents, package documentation and capture authority, duplicate-name package identity stability, strict reopen and declaration reordering controls. This is a historical salvage candidate with source-level controls, not proof that its whole old file can be cherry-picked into current vocabulary. The current selected-source, declared-member scope, signature carrier and typed fault changes must survive a narrow adaptation.

The required real probe uses two Go packages with the same type/function/member names, an external-test package of the same spelling, package documentation in `doc.go`, and both a same-package and imported reference. Require unique canonical addresses, exact source/reference targets, public package docs and cold equality after selecting and reopening. First establish whether the current compilation-unit/publication join already separates those package identities; do not call a confirmed collision based only on the missing module field.

## Cache and RAM: benchmark the operation the claim actually names

Old `1ec859f8aef06507efb72f021de334df466adfd2` introduces Pijul historical replay and a GCRA-gated Moka ServeCache. Its ignored `workspace/nudox-ir-vcs/tests.rs:506–629` benchmark generates 1,500 synthetic functions, six versions and eight edits per step; it times materialization, archive seal/read and one-symbol checkout. Its assertions compare age dependence and partial-read speed. It does not sample RSS, native compiler allocation, a public service or sustained concurrency. The commit's approximately 12× archive-read claim is tied to that reported small workload and operation.

The real old cache path, pre-cutover `repo/mod.rs:1803–1827`, materializes and seals every miss before asking the admission gate whether to retain the result. A throttled read still allocates the materialized index and newly sealed archive. Returned `Arc` owners can keep bytes alive after eviction. The gate regulates retained-entry frequency; it does not bound all working or caller-held memory and does not prove a repeated scan can never displace hot entries under every rate/workload.

There is also an old advertised-bound limitation worth avoiding during salvage: `serve_cache.rs:84–92` accepts a `u64` capacity but clamps each byte weight to `u32::MAX`. For a capacity above 4 GiB, an archive above 4 GiB can be charged less than its true length. `SealedArchive.bytes` and cache insertion are public, so this is a direct API counterexample to an unconditional byte-bound claim. The archive sealer additionally allocates section buffers and the assembled output. Section opener caps do not make caller-held/cached working memory equal the retained weight. No multi-GiB allocation or actual old product workload was run; this is a source-level defect in a deleted cache contract, not a current RAM regression.

These paths are actually used by the adapter and semantic/query/graph/diff projections; they are not merely benchmark-only helpers. Their exact authenticated key/claim/source laws are stronger foundations than an old version label cache. They should survive any admission-policy tuning.

The new benchmarks demonstrate different facts. `semantic_snapshot_residence` invokes `view_build/image_rows.rs:1097–1185`: 32 salted Rust fixture images, 32 samples, cold setup per sample versus the same snapshots/residence reused warm. It asserts 1,024 cold reopens, zero warm reopens and zero repeated validation on a resident proof miss. The separate `semantic_generation` calls `generation_residence.rs:372–435`: an actually compiled tiny two-file Clang fixture, prepared before timing, and requires the same Arc allocation with no owner call on a hit. Neither samples RSS or represents TS/Python/Go package compiler state. The image-reopen benchmark similarly times one versus three reopens and projection, not process memory.

There are real RSS diagnostic hooks in another domain: ignored `discovery_search/release_projection.rs:1082–1174` records `ps -o rss=` around 320 generated releases/16k aliases, and the next diagnostic exercises 10k releases. They measure lexical release projection and query latency. Their logical byte estimate and RSS delta are separate outputs. They do not establish semantic compiler cache RAM. A recorded diagnostic pass must name its checkpoint, input, build profile and retained process state before being extended into any claim.

The decisive RAM experiment should hold the same admitted actual TS/Python/Go package corpus and public queries constant, record cold/warm/re-add/restart latency plus RSS and per-owner retained/borrowed/in-flight bytes, then sweep more generations than each cache budget while holding and releasing active readers. Include bounded misses, simultaneous query/page work, and refused refresh retaining prior generations. Measure after worker completion and after caller references drop. A reduction in validation calls or a cache hit is useful evidence for its own operation; it is not substitute evidence for aggregate memory or product acceptance.
