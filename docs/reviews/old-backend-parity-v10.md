This is a static source and documentation review. The historical checkout was read only. No Cargo, Nix, build, test, screenshot, or network validation was run. The historical tree has stale workspace member and path references in its root Cargo.toml and workspace/index/Cargo.toml, so it is useful as a capability and UX record but is not treated as a buildable architecture or as an instruction source. The comparison is therefore about user-visible and production contracts, with implementation details used only to locate ownership and loss of behavior.

## Executive result

The current product has a credible greenfield foundation for parity: a shared command and presentation registry, one authenticated local service boundary for desktop/CLI/MCP, versioned object and relation storage, bounded source discovery, seven syntax frontends, typed registry facts, and concrete Tantivy, Qdrant, Trustfall, and Turso adapters. Those capabilities are represented in current code at crates/library/command_registry.rs, crates/present/grammar.rs, crates/local-service/src/embedded.rs, crates/store, crates/local-service/src/builtin/ingest.rs, crates/engine/src/registry, and extensions/.

Full historical production parity is not established. The current desktop is still a shell around several placeholders: project creation and selection are not connected to a durable project catalog, package routes render textual lane placeholders, source and graph actions do not open live projections, settings exposes only a reduced-motion toggle, and the client currently constructs ProjectId::new(1). The current desktop persistence intentionally saves only local-path shelf entries, so package and project identities from the historical shelf can disappear on a restart. Current MCP has a generated command surface and loopback HTTP, but it does not expose the historical nine-tool/resource contract or the historical desktop setup/status/config-copy flow. The current product state writer also renames a temporary file without fsyncing the file and parent directory. These gaps block a claim that the greenfield storage preserved every historical capability.

The highest-risk unknown is live end-to-end behavior. Static adapters and unit-level fixtures show broad coverage, but the repository evidence reviewed here does not prove a fresh, warm, offline, corrupt-restart journey through the desktop, CLI, and MCP for all supported languages and all seven package ecosystems. C# and JavaScript/TypeScript MCP round trips need explicit acceptance coverage because they were named as prior failure areas and the current source only proves frontend-level structure, not a live multi-client journey.

## Product behavior worth preserving

The historical implementation has useful user contracts that survive the architecture change:

* A project panel must always distinguish loading, ready, and failed states, and an empty corpus must explain how to add or configure a project. An empty result must never look like a successful index.
* Search should offer one keyboard-accessible surface for structural and semantic results, with typed rows, trust/provenance state, and predictable focus and Escape behavior.
* Package and symbol pages should expose dependencies, dependents, releases, security, source, documentation, and references from the same selected identity. The user should not have to reconstruct a package from opaque node IDs.
* MCP setup should show whether the endpoint is listening, provide a copyable client configuration, and give a clear recovery path after a restart or port change. The old client_config_snippet behavior is a useful product contract even if the wire transport stays current.
* Registry facts should distinguish exact, approximate, unavailable, withheld, and privileged counts, and should preserve yanked, deprecated, retracted, removed, advisory, and forge provenance. Unknown must not be rendered as zero.
* Indexing should show progress and typed failures, ignore generated/build folders before descent, honor nested .gitignore rules, and continue indexing other files when one claimed file is too large.
* A warm restart should restore the selected project/package/document identity, while an offline restart should still let the user inspect cached content and should explain every unavailable remote fact.

Legacy implementation debt must not return:

* The old root manifest and index manifest contain stale workspace paths and vendor-specific patches. They are evidence of capability ownership, not a dependency blueprint.
* workspace2 duplicates the transition architecture. It must not become a second CLI, MCP, or storage authority.
* The historical ProjectStore is deliberately a small skeleton with incrementing IDs and forward-declared dependency resolution. Current durable identities should not regress to that behavior.
* Hand-maintained duplicated MCP tool implementations should not be restored; the current shared command/presentation registry is the right authority.
* Old account and cloud-gate assumptions should not be copied into a local-first path where the user only needs a local service and an explicit transport credential.
* Historical platform wording that labels every credential as macOS Keychain is a known wrong-language defect. Current labels must be derived from the target platform.

## Data and behavior that must remain recoverable

No migration is required for this review, but a greenfield store must not silently discard historical meaning. The current owners should retain or explicitly classify:

* Stable project, package, version, symbol, document, source-span, and forge identities; selected versions; route identity; active project; shelf membership; and revision/epoch.
* Package coordinates and aliases; dependency and dependent edges; release standing; exact, approximate, privileged, withheld, and unavailable download counts; advisory identifiers and severity; licenses; repository and forge provenance; checksums; archive size; acquisition receipts; and native metadata.
* Source producer/language profile, compile/native-authority state, syntax baseline, source paths, line spans, diagnostics, and typed degraded/unavailable causes for every supported language.
* Index generation, feed/git/sink watermarks, object locations, outbox/replay state, listing events, repository lineage, and schema version. A current object/relation equivalent is acceptable, but a missing historical read must be represented as unavailable rather than an empty success.
* Lexical field meaning and ranking inputs from the old Tantivy schema: package identity, exact and tokenized names, namespace, description, keywords, ecosystem, record/dependency/license/repository fields, quality, downloads, and popularity. Preserve schema/watermark/partial-index state.
* Semantic model/recipe identity, vector coverage, remote/local endpoint state, and graph query authority. A vector or graph answer must carry enough provenance to distinguish unavailable, degraded, and empty.
* MCP session/endpoint identity, transport and bearer configuration, resource URI meaning, tool schema version, and reconnect/error classification. A changed tool surface should be versioned or aliased.

## Validation performed and limits

The review validated repository membership and symbol/file references statically and will validate the new JSON with Python's standard parser and the patch with Git's whitespace checker. It intentionally does not claim Cargo, Nix, build, test, screenshot, live package, or network results. The historical root's stale metadata is recorded as a limitation, not treated as a current failure.

The reports in this branch are the only intended changes. Any source change, generated artifact, lockfile change, or unrelated worktree file is outside this review and must not be committed with it.

## Five most serious remaining parity risks

1. The desktop still exposes a partially wired shell: project identity is hardcoded, shelf/project persistence is incomplete, and package, source, graph, and settings actions do not consistently reach live projections.
2. Current MCP transport is healthy as a foundation, but its generated names/results/resources and missing desktop setup/status flow are not yet a proven contract for historical Claude/MCP clients.
3. There is no reviewed evidence of a single live all-language journey through ingest, search/read/references/graph, CLI, MCP, and desktop; C# and JavaScript/TypeScript remain explicit failure risks.
4. Product-state durability and restart recovery are incomplete: commit lacks file/parent fsync, and warm, offline, and corrupt restarts have not all been demonstrated with real project/package identities.
5. Typed registry, Tantivy, Qdrant, Trustfall, and forge owners exist, but the historical index catalog/ingest record families and seven-ecosystem/forge facts are not yet proven end to end in the current production UI and client surfaces.
