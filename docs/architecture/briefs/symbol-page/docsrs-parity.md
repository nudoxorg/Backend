# FACET vs docs.rs — symbol-page gap matrix

Scope: read-only audit. Versions used (matched to what's cached under
`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/` and walked by
`Nudox-Design-System/v4/graph/extract.mjs`'s own CLI list): toml 0.8.23,
smallvec 1.16.0 (docs.rs fetched against 1.16.2, no schema-relevant diff),
serde_json 1.0.151, serde/serde_core 1.0.229.

Three systems compared throughout:
- **prototype** = `Nudox-Design-System/v4/graph/{extract.mjs,world.json,page.js,releases.*}`, a token-level JS parser + hand-written renderer. Its own CLI crate list (extract.mjs:652-657) is exactly toml/smallvec/serde_core/serde_json + the backend workspace.
- **engine** = the real production pipeline: `crates/engine/src/driver/lower/rust.rs` (ra_ap_hir-backed semantic lowering) → `crates/library/view/model.rs` (`Row`, `Fragment`, wire model) → `apps/desktop/src/runtime/page_mapping.rs` (assembles `SymbolPage`).
- **desktop** = `apps/desktop/src/model/pages/symbol.rs` (read model) rendered by `apps/desktop/src/shell/bodies/symbol.rs` (the actual production body today).
- A fourth system exists and matters for recommendations: **facet anatomy** = `apps/facet/src/anatomy/{fork,holds,contract,pipe,does,prism,in_use,can}.rs` plus `apps/facet/src/semantics/{bounds,caps,relations,members}.rs` — a full, already-built GPUI port of the prototype's rendering *and* its bound/cap/arrival logic, driven off `apps/facet`'s own `graph::model::World` (fixture-fed), **never imported by `apps/desktop`** (confirmed: `rg -ln "facet::anatomy" apps/desktop` = zero hits).

# What docs.rs cannot show and we can — our opportunities

**Real callers in your own tree ("In use").** The prototype's `inUse()` (page.js:241-274) fetches actual caller source, finds the real statement that uses the symbol, and shows syntax-highlighted code with the symbol bolded — something no docs.rs page can do, because docs.rs has no concept of "your repo." `apps/facet/src/anatomy/in_use.rs` is a complete, already-built GPUI port of exactly this (caption = caller link + `package · file:line`, code kept on its own lines, symbol underlined). **It is not wired into `apps/desktop`.** The desktop's own `usage()` (bodies/symbol.rs:538-570) only lists bare reference-site names/file/line under the Usage lens — no code snippet. This is close to a pure wiring gap, not a data gap: `page.references` (Known<Arc<[ReferenceSite]>>) already carries byte spans (`FileSpan`); rendering the actual source around that span is the only missing step.

**Since / changed-in a specific version.** `Nudox-Design-System/v4/graph/releases.json` + `releases-ui.js` compute pairwise API diffs (`added`/`removed`/`changed`, `breaking` vs not) between any two pinned versions of toml or smallvec (not yet serde/serde_json). This is real "what changed" data docs.rs never shows (docs.rs shows one version at a time, no diffing). Desktop's equivalent, `Lens::History`, is an acknowledged stub: `apps/desktop/src/shell/bodies/symbol.rs:59-62` literally renders "No release history is recorded for this declaration yet." for every declaration — the feature doesn't exist in production at all yet, prototype-only. Note the prototype's diff is pairwise-pinned, not a true "introduced in v0.X" — a real "since" fact would need a full-history walk, which neither system does today.

**Cousins and conversion chains.** `page.js` `cousinsOf()`/`cousins()` (page.js:342-373) finds "the same idea in another package" by Jaccard similarity over public method-name sets, then `recipes.js`/`apps/facet/src/semantics/recipes.rs` (1576 lines — a serious piece of engineering) computes a concrete "road" of conversions (From/TryFrom/method chains) between two types. docs.rs has nothing like this — it can't know your dependency graph contains both `toml::Value` and `serde_json::Value` and that there's a 1-hop road between them. Desktop has zero equivalent; `apps/facet` has the logic (recipes.rs) plus `apps/facet/src/graph/road.rs` but again unwired to `apps/desktop`.

**Capability arrival ("how it can, in plain words").** `apps/facet/src/semantics/caps.rs` already turns derives/impls into plain-word capabilities ("copies freely", "sorts", "prints") each marked hollow/solid/dashed for derived/written/via-another-capability — a friendlier and more scannable summary than docs.rs's flat trait-impl list. Desktop has nothing like it (bodies/symbol.rs has no "can" line at all).

# Ranked: 15 biggest gaps (by how much a reader misses)

1. **No anatomy shape at all in production.** docs.rs (and the prototype) visually distinguish "one of" (enum), "made of" (struct), "you write / you get" (trait contract), "takes → gives" (function pipe). `apps/desktop/src/shell/bodies/symbol.rs` renders every kind through the same generic hero+docs+relations+ledgers template — a struct and a function look structurally identical. Fix: wire `apps/facet::anatomy::{fork, holds, contract, pipe}` (already built, `apps/facet/src/anatomy/{fork,holds,contract,pipe}.rs`) into `apps/desktop/src/shell/bodies/symbol.rs`'s `body()` dispatch, keyed on `page.identity.kind`. This is the single highest-leverage fix on the list because the component code already exists.

2. **Required vs. provided trait methods, invisible.** docs.rs's most basic trait-page fact ("you must write this one") has no field anywhere in the engine/desktop model (`Member` has no `required: bool`), even though the prototype already computes it trivially (`extract.mjs:310`, "does the signature end in `;`"). Fix: add `required: bool` to `Member` (apps/desktop/src/model/pages/symbol.rs:190-197), set it in `member_of`/`members()` (page_mapping.rs:503-566) from whether the row's captured text/excerpt ends before a body. Smallest, cheapest fix on this whole list.

3. **`Arrival::Blanket`/`Arrival::Auto` are dead code.** The type already distinguishes "written for this type" / "blanket" / "compiler auto trait" / "not reported" (apps/desktop/src/model/pages/common.rs:250-261), but every call site hardcodes `NotReported` (page_mapping.rs:623, 762, 802 — confirmed zero non-NotReported constructions repo-wide). A reader can never tell "I wrote this impl" from "the compiler gave it to me for free." Fix: at minimum, detect auto traits (Send/Sync/Unpin/...) as a closed list the way `apps/facet` already treats them conceptually, and mark blanket impls when the impl's self type is a bare unconstrained/foreign wrapper.

4. **Item-level deprecation is fully absent from the wire model.** No `Row`/`Fragment`/`Member` field carries `#[deprecated]` (Rust) or `@Deprecated` (Java — which the Java lowering *already* extracts and throws away, `crates/engine/src/driver/lower/java.rs:3361-3391`). The prototype at least has a boolean (`extract.mjs:212`). A reader has zero warning that a symbol is deprecated. Fix: add `deprecated: Option<Arc<str>>` (message, or empty string for presence-only) to `Row`; surface it in `DeclRef`; render a strikethrough/badge in `bodies/symbol.rs` hero.

5. **cfg/feature gates are invisible everywhere, 5 confirmed instances** (toml Display/FromStr, smallvec Serialize/drain_filter/const_new, serde_json raw_value's `RawValue::NULL`, toml `parse` feature on `Error::span`, serde_json `preserve_order`). Worse: on the real engine, a feature-gated item isn't merely unbadged, it can be **entirely missing from the index** because `RustFeatureControl` bakes in one fixed feature policy per index run (rust.rs:159) and cfg is used only to decide inclusion (rust.rs:381-410), never retained as a fact. Fix, ordered by cost: (a) retain the verbatim cfg-predicate string per item/impl as a new fact; (b) index under more than one feature combination, or at least surface *which* combination was used so "missing" isn't silently indistinguishable from "doesn't exist."

6. **Member/variant/field docs truncate to one line everywhere** (both systems). Only a *top-level* declaration gets the full multi-fragment `docs: Arc<[DocFragment]>`; every `Member` gets a single `summary: Option<Arc<str>>` (page_mapping.rs `summary_of`, line 494-501). This is exactly the class of bug called out in memory ("count-based tests cannot see field loss") applied to docs: a variant's second paragraph (e.g. serde_json's `preserve_order` note on the `Object` variant) is silently gone. Fix: give `Member` a `docs: Arc<[DocFragment]>` alongside `summary`, reusing `doc_fragments()` (page_mapping.rs:365-381) which already exists for the top-level case.

7. **No Errors/Panics/Safety section detection.** `Fragment` is flat Text/Code/Link/Break with no heading concept, so rustdoc's `# Errors`/`# Panics`/`# Safety` (which docs.rs bolds and separates) reads as ordinary prose, or is dropped by the prototype's first-sentence cap. Fix: detect these headers in whatever markdown-to-Fragment lowering exists, add a `Fragment::Heading(SectionKind)` or similar, style distinctly in `docs()` (bodies/symbol.rs:359-445).

8. **"In use" shows names, not code.** Desktop's Usage lens (bodies/symbol.rs:538-570) is a plain list of file:line; the prototype's real-code-snippet version (page.js `inUse`, 241-274) and its unwired GPUI twin (`apps/facet/src/anatomy/in_use.rs`) are both strictly richer than anything docs.rs offers. Fix: wire `in_use.rs` into the Usage lens using the byte spans already in `ReferenceSite.span`.

9. **No release/version history in production at all.** `Lens::History` is a literal placeholder string (bodies/symbol.rs:59-62); the prototype's `releases.json`/`releases-ui.js` pairwise API diff exists but only for toml/smallvec, and desktop has nothing. Fix, incrementally: port the diff algorithm (`releases.mjs` normalizeText/diff) behind the same `symbol_page` boundary as a new `Known<VersionHistory>` field, starting with locally-registry-available crates.

10. **Deref-derived methods entirely absent** ("Methods from Deref<Target=[T]>", ~150 slice methods on SmallVec). Highest engineering cost on the list (needs std/core indexed, plus a synthesis pass), but also one of docs.rs's most-used sections for any newtype/smart-pointer-like type. Cheapest partial fix: when a `Deref` impl edge exists (already captured, `extract.mjs` STD_TRAITS resolves it, and the real engine's compiler graph almost certainly emits the same `Implements`-style edge), render a one-line "also behaves like `&[T]}`, N methods not shown here" instead of full enumeration — much cheaper than indexing std.

11. **Blanket impls onto reference/wrapper types silently vanish**, even when written in-repo/in-dependency source (serde's `impl<T:Serialize> Serialize for &T`). Root cause is shared with #3/#10: neither pipeline's "resolve the impl's self type" step handles `&T`/`Cow<T>`/`Box<T>` self types. Fix: extend `paths()`-equivalent self-type resolution (extract.mjs:283, page_mapping.rs `derive_impl_blocks`) to peel one layer of `&`/`&mut`/`Cow`/`Box`/`Rc`/`Arc` before giving up.

12. **Auto traits (Send/Sync/Unpin/...) never computed**, structurally impossible for the prototype (no source to read), genuinely possible for the real engine (ra_ap_hir can answer this) but not attempted. Lower priority than #3 because it requires real compiler-query work, not just plumbing a field.

13. **Macro signatures are near-empty** (`macro_rules! name`, no pattern/arms) in the prototype; unconfirmed-but-likely-thin in the real engine. Low reader impact (macros are a small fraction of any Rust API) but cheap to partially fix: capture the token range up to the first `=>` in extract.mjs, matching what `fn`/`struct` already do.

14. **No "not dyn compatible" / object-safety note.** Purely cosmetic relative to the above, but it is a fact docs.rs states plainly (§3) and neither system computes.

15. **Provenance/confidence/arrival computed but never rendered.** Even where the data model *does* carry something better than docs.rs (`Provenance::Semantic(SemanticConfidence)`, `Provenance::Derived{via,confidence}`, `Provenance::ByName`), `bodies/symbol.rs`'s `relation_link()` (line 502-536) renders every relation identically — a compiler-proven `Implements` edge and a same-package name-guess look the same to the reader. Fix: a small confidence dot/label, reusing data that already exists (no new indexing needed — purely a rendering gap, similar in shape to #2).

# Cross-language notes (design must generalize)

- **"Methods from Deref<Target=[T]>" (#10).** Rust-specific mechanism name, but the underlying reader need — "this type also acts like another type for free" — maps to: TypeScript/Go **interface embedding** / structural extension (`interface B extends A`, Go's embedded struct promoting fields+methods); Python **MRO inheritance** (`class Foo(Base):` — attribute/method lookup falls through the MRO chain, `__getattr__`/`__getattribute__` delegation for proxy-like classes); Java/C# **implicit conversion + delegation** is rarer (no operator-overload-based deref), closer to explicit wrapper/delegate patterns or Kotlin-style `by` delegation if present; C++ **`operator->()`/`operator*()`** on smart pointers is the closest 1:1 analogue, plus public inheritance exposing base-class methods. Any UI for this should be phrased as "acts like ⟨target⟩" generically, with the target computed per-language (Deref target / base class / embedded field / MRO parent), not as a Rust-only "Deref" concept.

- **Required vs. provided methods (#2).** Directly: Java/C# **interface default methods** (`default` in Java 8+, C# 8 default interface methods) vs. abstract-required; TypeScript **interface** members are always "required" (no default-method concept, though abstract classes have both); Python **ABC** (`abstractmethod` vs. a concrete method on the base) is the same idea with duck-typing weakening enforcement; Go has **no default methods** at all (interfaces are pure method sets, every method is "required" by definition — this axis genuinely collapses to nothing for Go, worth stating explicitly rather than forcing a UI split that never has two groups).

- **Blanket / auto impls (#3, #11, #12).** Rust-specific vocabulary, but the underlying facts have analogues: TypeScript **structural typing** ("any object shaped like X satisfies X" is Rust's blanket-impl idea turned up to eleven — TS has no separate "impl" step at all, satisfaction is automatic); Go **implicit interface satisfaction** (any type with the right method set satisfies an interface with zero declaration — closer to "everything is a potential blanket impl"); Java/C#/Python have no equivalent (impls/interfaces are always explicit `implements`/`:`/nominal registration) — for those languages this whole gap class is moot, and the UI should not show an empty "blanket impls" section, it should not show the section at all.

- **cfg/feature gates (#5, #9 item).** Direct analogues: npm/Node **`package.json` `optionalDependencies`/conditional exports** or bundler `#if`-style dead-code-elimination flags; Python **`sys.version_info`/`TYPE_CHECKING`/extras_require** optional-dependency gating; Java/C# have no first-class source-level feature-flag mechanism as pervasive as Rust's `cfg` (closest is Maven/Gradle profiles or `#if` in C# via conditional compilation symbols, `DEFINE` constants) — C++ **`#ifdef`/`#if defined(...)`** preprocessor gating is the closest 1:1 analogue and is *already* a known-hard problem for the C++ frontend generally. The design should treat "predicate text + enabled-by-what" as a generic optional field, not assume every language has it.

- **Item-level deprecation (#4).** Broadly universal and should be the *easiest* cross-language win: Python `@deprecated`/docstring convention, TypeScript `@deprecated` JSDoc tag, Go `// Deprecated:` doc-comment convention (checked by `staticcheck`/`go vet`), Java `@Deprecated` (already partially extracted per crates/engine/src/driver/lower/java.rs), C# `[Obsolete]`. A single `deprecated: Option<Arc<str>>` fact on `Row` covers all six languages with one field; this is the strongest argument for prioritizing #4 highly — it is both cheap and universal, unlike the Rust-flavored Deref/blanket-impl gaps.

- **Required doc sections (#7, Errors/Panics/Safety).** Convention-based in every language (Rust's `# Errors` heading is itself just a markdown convention, not a language feature) — Python docstrings (`Raises:` in Google/NumPy style), TypeScript JSDoc (`@throws`), Java Javadoc (`@throws`/`@exception`), C# XML doc (`<exception>`). A generic "structured doc section" fact (kind: Errors/Panics/Safety/Examples + body) is directly portable to a per-language convention-detector, and is worth building once, generically, rather than as a Rust-only heuristic.

# Summary (10 lines)

1. Production desktop (`apps/desktop`) renders every declaration through one flat template — no fork/bundle/contract/pipe shape distinction docs.rs and the prototype both have.
2. A fully-built, richer GPUI component library for exactly this (`apps/facet::anatomy`, plus `bounds.rs`/`caps.rs`/`relations.rs`) already exists and is completely unwired to `apps/desktop` — the single biggest, cheapest win is plumbing, not new engineering.
3. Required-vs-provided trait methods and item-level `#[deprecated]` are two cheap, high-value facts the prototype already half-computes and the engine doesn't carry at all.
4. `Arrival::Blanket`/`Arrival::Auto` are modeled types with zero real constructions anywhere in the repo — dead code masking a real data gap.
5. cfg/feature gating is invisible everywhere (5 confirmed instances) and, on the real engine, can mean an item is silently missing from the index entirely, not just unbadged.
6. Member/variant/field docs are truncated to one line in both systems; only top-level symbols get full multi-paragraph docs — the same "count vs. content" failure mode flagged elsewhere in this codebase's own memory.
7. Blanket impls onto `&T`/`Cow<T>`/wrapper types are lost in both pipelines because self-type resolution never peels a reference/wrapper layer.
8. "Methods from Deref" is the single highest-effort gap (needs std indexed) but has a cheap one-line partial fix available now.
9. FACET's genuine advantages over docs.rs — real in-tree callers, cousins/conversion roads, capability-arrival wording — are mostly built in `apps/facet` already and simply not connected to production.
10. Cross-language generalization is uneven by design, not oversight: deprecation and doc-sections generalize to all six languages cheaply; Deref-methods and blanket/auto impls are Rust-heavy concepts whose closest analogues (interface embedding, MRO, structural typing) genuinely don't exist symmetrically in Go/Java/C#, and the UI should degrade gracefully (hide the section) rather than force an empty analogy.
