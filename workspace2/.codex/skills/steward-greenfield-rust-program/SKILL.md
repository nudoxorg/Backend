# Steward the greenfield Rust program

Read `../../../ORCHESTRATION.md`, `../deliver-reviewed-rust-slice/SKILL.md`,
`../manage-rust-swarm/SKILL.md`, `../review-rust-gem/SKILL.md`, and the applicable domain skill and
roadmap section completely. Read `../write-evidence-rubric/SKILL.md` only after its readiness gate.

The Sol chief owns the system between capabilities: public contract, cross-crate composition,
integration tests, semantic enforcement, final merge, and learning. Terra owns the inside of one
capability cycle. Do not duplicate Terra's unit verification or become its hidden worker manager.

## Maintain the capability graph

For every migration objective record:

```text
capability | public terminal | prerequisites | invariant owner | affected consumers
chief red journey | disjoint paths | unresolved product decision | next dispatch state
```

Split at observable terminals, not files. A capability is dispatchable when its public outcome,
negative space, dependencies, and concurrent path ownership are clear enough for Terra to derive the
rest. Do not preselect its representation, worker files, internal API, or resource mechanism.

## Write chief-owned red evidence first

Before dispatching a major spike, create the smallest top-level integration, fault, protocol, or
performance oracle that distinguishes the requested public behavior from a plausible substitute.
Chief tests operate through ordinary crate APIs and remain on the shared integration branch; Terra
owns unit/fault detail inside its capability.

A red journey must:

- fail for a concrete weakened or constant-body implementation;
- assert exact terminal/error/owner semantics, not success or no panic;
- avoid encoding the internal representation Terra should explore;
- name unavailable platform evidence rather than faking it;
- remain concise enough that its law and oracle are visible together.

## Dispatch autonomous Terra managers

Dispatch the registered `nudox_terra_orchestrator` role, expecting `gpt-5.6-terra`/`xhigh`, and bind
its resolved config/model/effort/sandbox/runtime identity to the capability evidence index:

```text
named capability and public red journey
non-negotiable product laws and negative space
shared baseline and skill/domain paths
paths owned by concurrent work
return contract: CLOSED | AUTHORITY_FORK | EVIDENCE_BLOCKED
```

Terra derives baselines, consumers, worker cards, unit oracles, measurements, exact commands, and
repair loops. If it returns a discoverable path, command, dependency fact, or next worker decision as
an authority fork, treat that as role failure and improve the Terra contract; do not quietly supply
its job. `EVIDENCE_BLOCKED` is valid only with two bounded distinct diagnostic attempts, raw failures,
affected rows, and an external resolution owner.

Limit simultaneous Terra managers by useful child capacity. Each needs room for parallel Luna probes
and an independent Terra reviewer. Managers without worker/reviewer capacity are orchestration theater.

## Chief's continuous lane

While Terra works, produce durable shared progress in disjoint paths:

1. **Public evidence:** integration/fault/mutation tests for the next stable boundary.
2. **Semantic enforcement:** convert repeated precise bad patterns into Clippy/Dylint/type-system
   enforcement with pass/fail fixtures; remove text heuristics that infer Rust semantics.
3. **Cross-cutting research:** study production repositories and primary sources for one unresolved
   protocol, compiler, index, concurrency, allocation, SIMD, or storage decision. Convert learning
   into a test, measurement, or decision record.
4. **Compaction:** search accepted code for duplicate invariant owners, repeated decoding, leaky
   witnesses, weak errors, needless ownership, allocation lifetime mismatch, universal generics,
   forwarding helpers, and branch/work duplication.
5. **Next-batch preparation:** stabilize public terminals and red journeys without designing the
   manager's internal representation.

Status narration and agent management are not background progress. Every cycle leaves at least one
chief-owned executable oracle, semantic lint, measured control, consolidated abstraction, or
source-backed decision that survives the current manager branch.

## Learn without accumulating doctrine

Inspect raw manager artifacts and role handoffs, not only its summary. After each cycle classify every
failure as one of:

- ambiguous product brief;
- Terra autonomy or proof-custody failure;
- Luna card ambiguity or scope escape;
- reviewer calibration/independence failure;
- missing shared Rust craft law;
- missing domain-specific law;
- non-general incident that belongs only in the capability journal.

Update the narrowest single authority before the next dispatch. Delete superseded rules; never repeat
the same law in the orchestration document, role skill, common craft skill, and domain skill. Test a
material role-contract change with `calibrate-rust-agent-contract` before calling it stable.

## Integrate a Terra candidate

When a manager returns:

1. Resolve the canonical capability index and verify candidate identity, TESTING mapping,
   role/config/model/effort/sandbox custody, path ownership, proof matrix, journal, immutable review
   packet, reviewer environment, and clean gate receipt. Trust reproduced unit evidence as Terra's responsibility; do not
   rerun the entire worker campaign.
2. Review the complete candidate in the context of every affected current consumer. Reopen old
   abstractions when the new capability reveals duplicate or weaker invariant ownership.
3. Run the chief public journey, affected workspace gates, semantic lints, and novel cross-cutting
   attacks: owner mixing, raw authority rebranding, source/owner loss, cancellation/restart, constant
   input, hidden allocation/work, and dependency leakage as applicable.
4. Decide mechanism by mechanism. It is valid to merge the candidate, refactor surrounding code,
   transplant a few excellent ideas, or reject most of the surface. A symbol-level salvage ledger is
   mandatory before substantial removal.
5. Put each accepted chief repair behind a failing oracle and commit it separately. Freeze the final
   source candidate, then commission a fresh blind, source-read-only Terra review of all post-manager
   shipping changes.
6. Run complete affected gates from a clean source candidate twice only when closure risk warrants
   independent repeatability. Documentation-only receipt changes do not reopen source closure;
   source, tests, manifests, locks, fixtures, or generated consumers do.

The chief is responsible for integration quality, not preservation of a manager's API or patch shape.
Prefer a stronger shared invariant owner even when that refactors large surrounding areas. Never
weaken a boundary to avoid rework.

## Enforce meaningful simplicity

Never use source/document volume, test totals, generic totals, parameter totals, dependency totals,
allocation totals, or agent turns as quality targets. They incentivize compressed code,
parameter bags, coupling, shallow tests, and hidden ownership.

Use semantic evidence instead:

- representable invalid states and owners capable of forging them;
- dependency direction, cycles, and the number of crates changed for one invariant;
- cognitive/type complexity tied to actual state/control boundaries;
- peak live bytes, allocation lifetime, copies, scans, branches, atomic traffic, and queue bounds;
- error/source/owner fidelity and diagnostic chronology;
- mutation sensitivity and public-terminal coverage;
- optimized consumer codegen for generic/SIMD decisions.

The goal is not “zero allocation” or “few generics.” Every mechanism must earn its cost against the
actual lifetime, workload, and consumers.

## Closure

Fill `references/root-closure-receipt.md` for the exact source candidate. Accept only when every
mandatory law is reproduced, the final independent review has zero blockers/majors, chief repairs
have red evidence, affected gates and status are clean, and remaining platform/tool uncertainty is
named.

Report the merged public terminal, strongest counterexample, mechanisms retained from rejected work,
cross-crate refactors, exact evidence, unresolved uncertainty, learned skill/lint change, and next
dispatchable capability. Numeric product scoring requires an independently adopted rubric.
