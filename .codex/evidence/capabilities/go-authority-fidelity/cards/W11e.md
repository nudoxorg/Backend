## The defect (manager-verified on golang.org/x/sync@v0.10.0)

`Projector::alias` pushes the alias fact and calls `record_name`, but —
unlike `named_type` (line 468), `function` (676), and `value` (728) — it
never writes `self.declaration_ordinals[index]`. Any later pass that
addresses a declaration row which is an ALIAS — declaration docs, a
local reference target, a satisfaction subject — finds `None` and folds
through `terminal(ProjectionFault::OrphanOwner { owner: <index> })` into
`NoSupportedDeclaration`. Observed live: the whole-module journey dies
with `OrphanOwner { owner: 62 }` once a real module with a documented
alias is projected.

## Required repair

`alias()` takes the declaration's index and registers
`self.declaration_ordinals[index] = Some(ordinal)` after the push, the
same law as its sibling passes; `collect`'s alias loop passes the index
it already has. No other registration or ordering changes: pass one
(types), the alias sub-pass, then pass two remain the anchor order.

## Required falsifier (extend an existing test)

Extend `aliases_project_their_target_records` (or add one adjacent test)
so that after the alias projection the fixture also carries ONE image
row that addresses the alias declaration by index — a declaration doc
row (`DocOwner::Declaration`) is the cheapest — and assert the doc
lands on the alias fact's ordinal (decode via the typed docs cursor).
On the unfixed code this exact shape faults `OrphanOwner`; on the fixed
code it must pass with the alias fact carrying its extension row cells
(zero constant cells) unchanged.
