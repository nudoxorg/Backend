# Source byte continuation process observation

The two JSON receipts retain an actual isolated run against matching official
Backend 0.3.0 T1 applications from
`55551f420a870ddf55e93ed0117bbabc815ec612`. The candidate driver was built from
Keel `6764b2a09dea7a84d9a42d59fa732639410f75aa`; its executable SHA-256 is
`e5219d43396081413c5815b17862b0125a37fda4dfb50bcefedc647467ffdc5d`.
Every product process ran inside a required cgroup-v2 boundary. This is an
identified diagnostic, not qualification of later product source or the full
release inventory.

The independently authored TypeScript source has a primary declaration after
more than 4 KiB of padding, with multibyte text and CRLF line endings. Four MCP
pages and four independently requested CLI pages reconstruct its exact 6,714
UTF-8 bytes. The driver checks contiguous byte geometry, source identity,
scope, owner extent, revision, selected-symbol identity and coordinate. The
scope is `native_primary_declaration`; this is not a claim of whole-file or
merged-declaration completeness.

The same fixture issues a source continuation, stops and reaps MCP, restarts
the owner, starts a new MCP process and resumes that continuation. A same-size
on-disk edit then makes the retained cursor fail with `invalid-query`, operand
`source`, cause `malformed`, and the explicit instruction to reindex because
the indexed source changed. The fault returns no source bytes.

The first report, `source-range-oracle-failure-55551-6764-20261116.json`, is
preserved as failed evidence. Its draft assertion expected `cursor-mismatch`
for that last refusal. The raw reply already contained the correct explicit
source-changed refusal. The corrected fixture keeps that semantic requirement
and checks the actual typed fault rather than accepting an arbitrary error.
The second fresh run passed all 12 steps; report SHA-256 is
`103922c62505fdbd97a9c76541570ebee01a31f4b5c0cbba96e8a350c343fda7`.

remain on ilo-prod under
